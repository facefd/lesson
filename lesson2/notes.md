# Диагностика: сервер "не глухой", но вы этого не видите

## Задача 1: Результаты диагностики

После запуска проекта (старая версия без middleware) и выполнения запросов:
- GET /index.html, GET /api/tasks, GET /api/hello, GET /api/sum?a=5&b=3

Установлено: в консоли Visual Studio не отображается НИКАКОЙ информации о запросах.
Сервер "не глухой" (отвечает корректно), но разработчик не видит, кто и когда обращается.

## Задача 5: Поведение ДО исправления (без route constraint)

Маршрут GET /api/tasks/{id} без ограничения :int при запросе /api/tasks/abc
вызывал бы ошибку 400 Bad Request (не удалось преобразовать "abc" в int)
или некорректное поведение. После добавления {id:int} → чистый 404.

## Задача 6: Эксперимент с порядком middleware

Если middleware логирования зарегистрировать ПОСЛЕ MapGet/MapPost, то
обработчики endpoint'ов выполняются раньше middleware — в консоли вообще
не появляется логов запросов (маршрутизация заканчивает конвейер до
логирующего middleware для запросов с совпавшим маршрутом).
Порядок регистрации = порядок выполнения: middleware в начале конвейера
видит ВСЕ запросы, в конце — только те, что дошли до него.

## Вывод

Все задачи реализованы и протестированы. Сервер логирует каждый запрос
(метод, путь, статус, время), защищён от некорректных ID (404), требует
API-ключ для изменения задач (401), возвращает аккуратный JSON при ошибках (500),
поддерживает режим техработ (503), ограничивает частоту запросов (429).
